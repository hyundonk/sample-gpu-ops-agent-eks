Design Principles

설계 철학 — "결정론은 Karpenter에게, 판단은 Agent에게"

AI가 인프라를 마음대로 바꾸는 시스템이 아니라, 판단이 필요한 지점에만 AI가 개입하는 시스템입니다.

역할 경계 — 무엇이 자동이고, 무엇이 판단인가

Karpenter · KEDA만으로 처리 (Agent 불개입, 수 초)
  • 가용영역 재시도 — 한 AZ 실패 시 타 AZ 자동 시도
  • 상시 사다리 폴백 — g7e Spot 부족 → g6e Spot 자동 전환 실전 검증 2초
  • 온디맨드 최종 폴백 — Spot 전멸 시 OD 자동 조달 (상시 개방, limits = 비용 캡)
  • 큐 기반 워커 증감 — 큐 깊이 따라 0~max 자동 (KEDA)
  • 유휴 노드 회수 — 빈 노드 30분 후 자동 반납
Agent의 판단이 필요 (수 분)
  • 원인 분류 — 용량 부족? 쿼터? GPU 스택 장애? (오진 = 최대 낭비)
  • OD 잠식 회수 + 예산 감시 — Spot 회복 시 OD 워커를 되돌릴지, 비용이 새는지
  • 노드 보유 연장 — 공급 부족 추세 판단 후 회수 지연
  • 큐 완충 — 조달 가능한 수준으로 수요 상한 정렬
  • 스택 복구 — "노드는 정상인데 GPU가 안 보임" 진단·복구
  • 리전 확장 — 언제, 어느 리전을, 어떤 조합으로 열지
  • 에스컬레이션 — 자동 조치가 무의미할 때 구조화 리포트로 사람에게
📐
경계 기준: 기계적으로 확실하면 결정론 계층, 상태·비용·추세 판단이 끼면 Agent. 가용성 대응은 전부 결정론 계층이 즉시 처리하고, Agent는 그 뒤에 비용을 회수합니다.
⚖️
결정 필요: SLO 대 비용 우선순위 — 본 구성은 가용성 우선(온디맨드 상시 폴백 + 사후 비용 회수)입니다. 비용 우선(온디맨드 잠금 + AI 사전 허가) 구성으로의 전환은 값 하나(limits)이며, 이 우선순위는 고객 사업 판단으로 최종 확정이 필요합니다.

Architecture

전체 아키텍처 — 실배포 구성 (서울)

알람이 뜨면 사람 손 없이: 게이트(중복 제거) → AI 판단 → (Shadow) 리포트까지 완주합니다.

실선 = 제어 흐름 · 점선 = 데이터/보조 흐름 · 붉은 계열 = write 경로(가드레일 통과) · 파란 계열 = AgentCore 구성요소

Task #1 · Cluster & Fallback Ladder

사다리형 NodePool — 저비용부터 자동 폴백

저비용(Spot)부터 시도하고 부족하면 자동으로 다음 계단으로 — 최종 계단(온디맨드)까지 상시 개방하되 limits로 비용을 캡.

D 핵심 설계 결정

weight 사다리 — g7e Spot MIG(100) → g6e Spot(80) → 온디맨드(60, 상시 개방 · limits = 비용 캡). 폴백 전 단계가 Karpenter 내장 동작(수 초) — 가용성 대응에 AI 개입 없음. Agent는 사후 비용 회수 담당.
구성 vs 런타임 분리 — 사다리 구조·상한은 Git(코드리뷰), 게이트 개폐는 런타임(Agent). 환경 변화가 코드 변경을 유발하지 않는 원칙.

Task #2 · Queue, Worker & KEDA

중앙 큐 + KEDA — 라우팅 계층 없는 멀티리전의 기반

세 리전의 KEDA가 같은 큐를 바라보므로 "어느 리전이 일하는가"는 게이트 개폐 하나로 결정됩니다.

D 설계 결정

연합(federation) 없는 멀티클러스터 — 중앙 Valkey 큐 + 리전별 KEDA. 작업 분배가 자연 발생, 라우팅·스케줄링 계층 자체가 불필요.
작업 보존: drain 우선 + 반환(re-push) 폴백 — Valkey는 SQS와 달리 "꺼냄 = 삭제"라 브로커가 작업을 지켜주지 않습니다. 워커가 종료 신호를 받으면: 남은 작업이 짧으면(mesh 생성 20~30초) 완주 후 종료(drain) — 낭비 연산·중복 처리 0. 완주 불가 시에만 큐에 반환. Spot 중단 2분 경고·게이트 원복 모두 이 경로.

✓ 검증 결과

  • 30건 주입 → KEDA 확장 → 사다리 노드 조달 → 30건 전원 완주 → 워커 0으로 자동 축소
  • g7e MIG 검증 완결: 슬롯 2개 광고, 워커 2개 동거 (40GB급 모델 2개 = 인스턴스 1대)
  • 작업 보존 실증: 처리 중 강제 축소 → 미완료 작업 전량 큐 복귀 = 손실 0 (이후 drain 우선으로 개선 — 짧은 작업은 완주 후 종료, 반환은 안전망)

! 실측 발견 2건 — 문서 설계를 실물이 교정

발견설계 가정실측반영
limits는 광고 슬롯 기준gpu: 2 = 노드 2대MIG 노드 1대가 예산 2 소비설계서 §2.1 정정, 예산 산식 변경
KEDA max=0 불가리전 게이트 닫힘 = max 0CRD가 max ≥ 1 강제게이트 = pause 어노테이션으로 재설계 (write 도구 계약 변경)
⚠️
이 두 건이 데모의 존재 가치입니다 — Agent가 잘못된 API 계약으로 구현될 뻔한 것을 write 활성화 전에 잡았습니다.
Task #3 · Signal Layer

신호 계층 — Valkey 큐에는 CloudWatch가 없다

SQS와 달리 Valkey는 네이티브 메트릭이 없으므로, exporter가 알람 계층의 전제 조건입니다.

알람 3종 — 무엇을, 왜 그 조건으로 감지하나

알람조건의미와 예시
사다리 소진
Agent 트리거		 Pending 워커 ≥ 1
5분 연속 (Minimum 통계)		 Karpenter가 5분간 못 채움 = 전 계단 실패 추정. 정상 조달이 1~2분임을 실측했으므로 5분은 신뢰할 수 있는 경계 — 순간 Pending은 무시.
예: 큐 급증으로 워커 6개 요청 → Spot 두 풀 소진 + 온디맨드 캡 도달 → 2개가 5분째 Pending → 알람 → Agent가 원인(용량? 쿼터?) 분류.
GPU 미광고
Agent 트리거		 Ready 노드 중
GPU 0개 광고 ≥ 1대, 5분		 "노드는 살아있는데 GPU가 안 보임" = 용량이 아니라 GPU 소프트웨어 스택 장애. 정상 MIG 분할이 40초라 5분이면 확실한 이상 — 용량 오진 방지의 핵심 신호.
예: MIG 설정 오타 배포 → 분할 실패(state=failed) → 노드 Ready·GPU 0 → 알람 → Agent가 라벨 원복 계획 (40초 복구).
큐 SLO
Agent 트리거		 큐 깊이 > 40
10분 지속		 워커가 돌아도 수요가 공급을 구조적으로 초과하는 상태 — 일시 스파이크(수 분 내 소화)와 구분하기 위해 10분.
예: 이벤트로 큐 100건 유입, 워커 풀가동에도 10분간 40 이상 유지 → 알람 → Agent가 큐 완충·리전 확장 검토.
🔔
공통 원칙: 알람의 상태 전이(OK→ALARM)만 이벤트화 — 같은 장애가 인시던트 폭풍이 되지 않습니다. 재발성은 게이트의 쿨다운(30분)이 별도로 흡수합니다.

D 설계 결정

exporter Lambda가 K8s API를 직접 조회 — Prometheus 스택 없이 Pending 워커·GPU 미광고를 메트릭화. 이 접근 패턴(토큰 생성 + Access Entry)이 그대로 read 도구의 기반이 됨.
"사다리 소진" = Pending 5분 지속 — 정상 조달이 1~2분임을 실측했으므로, 5분 Pending은 소진/실패의 신뢰할 수 있는 근사.

✓ 검증 + 트러블슈팅 3건

  • 메트릭 4종 수집 + 알람→EventBridge→SQS 배선 E2E 확인
  • VPC Lambda → EKS 프라이빗 엔드포인트는 클러스터 SG 443 허용 필수 (도구 7종 공통 경로 — 선행 해결)
  • 관리형 View 정책은 nodes 등 클러스터 리소스 미커버 → 커스텀 RBAC 패턴 확립
  • 로컬 Helm 차트는 파일 추가만으론 변경 미감지 → 버전 bump 규칙화

Task #5 · AgentCore + Strands Agent

판단 파이프라인 — 첫 시험에서 오진을 거부했습니다

분류 → 조사 → 계획의 3단계. 조사 노드에만 도구가 있어 "조사 없이 액션"이 구조적으로 불가능합니다.

판단 파이프라인 구조 (pipeline.py) — multi-agent가 아니라 역할 분리된 순차 워크플로

System Prompt 요지 — 단계별로 다른 역할, 다른 규율

단계 1 · 분류 (도구 없음)
"장애 분류 전문가"
  • NodeClaim 에러 코드가 1차 근거
  • 쿼터 초과 ↔ 용량 부족 절대 혼동 금지 ("쿼터에 게이트를 열면 비용만 쓰고 해결 안 됨")
  • 노드 Ready + GPU 0 = 용량 아님, 스택 문제
  • 확신 없으면 needs_investigation=true — 오진이 가장 큰 낭비
단계 2 · 조사 (read 도구 바인딩)
"조사관"
  • 최소 호출로 결정적 증거만 — 가설을 확증/반증하는 데 필요한 것만 조회
  • 필수 확인 3종: NodeClaim 에러 코드 · 사다리 소진 여부(limit vs 사용량) · 큐 추세(수요 실재)
  • 조치 제안 금지 — "그것은 다음 단계의 일" (역할 침범 차단)
단계 3 · 계획 (도구 없음)
"대응 계획가"
  • 첫 문장이 "당신은 실행 권한이 없습니다" — 계획은 별도 시스템이 재검증 후 집행
  • 도메인 지식 명시: 온디맨드 폴백은 상시 개방이 정상 · 잠식 회수는 Spot 회복 증거 시에만(관망이 기본) · 해소된 인시던트엔 조치 금지
  • 제어 항목 4종의 정확한 호출 계약(키·값 형식) + 위반 시 어차피 코드가 거부
  • 모든 조치에 rollback 서술 필수 · 확신 없으면 에스컬레이션
📜
프롬프트는 설계 문서의 정책 조항을 코드화한 것입니다 — "쿼터 → 재시도 무의미", "관망이 기본" 같은 운영 규율이 그대로 들어가며, Git 코드리뷰 대상입니다. 아래 검증 ②의 오판 교정도 프롬프트에 도메인 지식 3줄을 추가한 것이었습니다.

Shadow 모드란 — 판단은 전부 하고, 실행만 하지 않는다

  • 동작: 실제 알람마다 Agent가 분류·조사·계획까지 수행하되, 실행 단계를 건너뛰고 리포트만 발송 (Step Functions 플래그 하나 — 인프라는 무변경)
  • 측정: 계획서와 사람 판단을 대조해 분류 정확도·조치 적절성을 채점 — AgentCore Evaluations로 자동화 (도구 선택·파라미터 정확도)
  • 졸업: 정확도 기준 충족 시 저위험 write부터 단계적 활성화 (아래 로드맵)
왜 필요한가 — 실수 비용의 비대칭
읽기 실수는 공짜지만 쓰기 실수는 시간당 과금(온디맨드)이거나 서비스 영향입니다. Shadow는 read/write 비대칭 설계의 시간 축 버전 — "쓰기 능력은 만들어두되, 권한은 증거가 쌓인 뒤에".
💡
실물 증거는 Task #5에서: Agent의 오판(불필요한 온디맨드 개방 계획)이 Shadow였기에 비용 0원의 리포트로 끝났고, 프롬프트 교정으로 이어졌습니다.
